# 长视频总结采用「阶梯 + Map-Reduce 分层归并 + 压缩摘要」而非单次满载

> 状态：有效｜2 处修订：预算抬至 200k 字符；补预算口径与「窗口 ≥256k」使用前提

「一键总结」目前把整篇字幕塞进单次请求，并硬截断到 5 万字符（丢尾部、无 token 感知）。我们决定：**素材预算定为 200k 字符**（现行值；2026-09-06 修订前的 100k token 值与其"100k 是模型最聪明区间"的定档依据均已作废，见文末。模型统一按 256k 窗口是**使用前提**，窗口不足时的回落边界见「后果」的使用前提条），预算内一次成稿；超出才进入**分段压缩 + 多层归并**（Map-Reduce）；多轮追问以**压缩摘要 + 近轮对话 verbatim** 为常驻上下文，原始字幕段仅在命中时间戳/章节/关键词时按需检索注入，取代每轮重发全文幕。

## 考虑过的方案

- **单次满载 + 提高截断阈值**：简单，但 5h 级字幕仍会溢出，且每轮追问重发全文幕，token 与成本随追问次数线性放大。
- **固定 90 分钟分段**：直接，但字幕密度差异极大，墙钟不是稳定单位；短/中视频也会被无谓拆段多花调用。
- **阶梯 + Map-Reduce（选定）**：预算内零成本，仅真正超长/极密才多花调用；预算内绝大多数视频一次成稿，Map-Reduce 只是少数情况。

## 后果

- 新增两个模块：**预算判定**（估 token → fits/overflow → 分段计划，纯函数）与 **Map-Reduce 编排**（跑在 offscreen 文档）；`streamChat` 退化为预算内单次路径。
- 只有 Map-Reduce 路径会产生多次调用（例如 110k 字幕 → 3 段小结 + 1 次成稿 ≈ 4 次调用），故**限并发 2~3**，并在预估 ≥5 次调用时弹成本护栏；预算内（≤200k 字符）视频永不拆段，仍是 1 次调用。
- 追问不再重发原始字幕，token 随追问近乎常数；代价是压缩摘要有损，靠原始字幕缓存回填细节。
- 分段边界：字符预算为纲 + 章节对齐，无章节按时间戳累积。
- 默认常量（可调；**单位一律为字符**——2026-09-29 就地校正，此前逐项写 token，与代码常量名 `..._CHARS` 及 `chars × 1.0` 的系数口径不合）：素材预算 200k 字符（2026-09-06 抬线前为 100k）；单段输入 50k；分段小结 10k/段（=20% 保留，对齐 Q1 完整忠实）；归并组输入 100k，归并仅在段数 ≥11（原始字幕 >500k）时触发；成稿输出 ≤ 16k；字符→token 按 `chars × 1.0`（每字符≈1 token）——该系数**只进成本护栏的展示数字，不参与任何判定**（阶梯比的是字符数与素材预算），「保守」的正确归属是下条 200k 字符对 256k 窗口的拟合前提，不是"宁可早进 Map-Reduce"；换成实测比例已于 2026-09-29 落地（成本护栏数字改用按 `(baseUrl, model)` 学到的响应 `usage` 实测比，无样本时回落本系数；阶梯判定仍比字符数与素材预算，判定路径零改），不再挂到窗口自适应那轮（重开条件见下条）。
- **使用前提（2026-09-29 就地补记）**：200k 字符预算按「模型上下文窗口 ≥256k」定档，窗口不足时靠**三级溢出回落**兜底，不是无限兜底——(1) 单发 HTTP context-length 溢出 → 转 Map-Reduce（`ai/ladder.ts`）；(2) 段调用仍溢出 → 单段输入 / 归并组输入收 0.5 倍整轮重跑一次（`ai/map-reduce.ts`）；(3) 再溢出 → 明确报「请更换上下文窗口更大的模型」。地板约在 32k 窗口级（单段降到 25k 字符仍装不下即失败）。代价值得知道：每次回落先白花一次单发请求；整条兜底依赖 `isContextLengthOverflow` 的平台错误文案启发式，平台换措辞就是一条 HTTP 400 硬错误而非自动分段。**重开条件**：要按窗口自适应预算，须先正面重开 ADR-0009（目录参与请求塑形），或走 per-provider 窗口设置——两者都不在既有裁决内。

## 修订（2026-09-06：素材预算抬至 200k 字符）

「100k 是模型最聪明区间」的保守前提按实际使用重新校准：所配模型窗口全部 ≥256k（此句 2026-09-29 起作为**使用前提**对待、不再是普遍事实——仓内目录里也有 200k 窗口的模型，边界见文末第二轮修订），实际视频一般不超过 7 小时（7h 中文访谈 ≈ 10-18 万字符 ≈ 9-13 万真实 token，`chars × 1.0` 估计显著偏高）。**`MATERIAL_BUDGET_CHARS` 100k → 200k 字符**（200k ≈ 256k 窗口 − 16k 输出 − 余量），其余常量不动：预算内一次成稿覆盖 7h 级长视频，15h+ 级或更小窗口模型仍走 Map-Reduce + 溢出回落链路。影响面：10-20 万字符视频的成稿与概览同转单发、长视频追问改重发全字幕、成本护栏在单发路径不触发。决策与验收记录见 commit 000b279。

## 修订（2026-09-29：预算口径就地校正，「窗口 ≥256k」升格为使用前提）

本轮不动任何常量与代码，只校正正文的口径与前提（沿用体例规则 1：失效数字与已裁决的未决句就地改，不靠文末注兜）：

- **正文的「100k token」更正为 200k 字符**（首段、「考虑过的方案」第三条、「后果」第三条、常量清单四处）：2026-09-06 修订已把 `MATERIAL_BUDGET_CHARS` 由 100k 抬到 200k，正文数字却留在原处；按正文自己声明的 `chars × 1.0`，旧值即 100k 字符，读者只读正文会照抄一个已翻倍的旧值。同时「100k 是模型最聪明区间」这条定档依据一并标作废——2026-09-06 修订的实测（7h 中文 ≈ 10-18 万字符 ≈ 9-13 万真实 token，`chars × 1.0` 显著偏高）说明抬线的理由是**估算偏保守**，修订后实际起作用的定档依据是**窗口余量**，两者不是同一条。
- **常量清单单位改为字符**：清单原先逐项写 token，而代码常量一律是 `..._CHARS`（`ai/budgeter.ts`）。数字因系数 1.0 恰好一一对应，故此前只是标签错。清单里的数字取自代码常量的字符值，与系数无关：系数只换算成本护栏的展示数字（用途与去向见上一条），改它不会让这些数字变成错账。
- **「模型统一按 256k 窗口」升格为显式使用前提 + 重开条件**（见「后果」新增的「使用前提」条）：它此前只是 2026-09-06 修订里的一句顺带事实，而 ADR-0012 同时承认「更小窗口的模型靠溢出回落」——两篇合读像「假设没有小窗口，有也兜得住」。补记三级回落的实际地板（约 32k 窗口级）、每次白花一次单发 400 的代价、以及整条兜底依赖 `isContextLengthOverflow` 文案启发式这三件事。ADR-0012 文末对应的一句已就地改为指向本条。
